# Reflexão e equivalência em nuvem


**Q1. Por que o `web` encontra o banco pelo nome `db`?** Porque o `rede_interna` é uma rede bridge definida pelo usuário, e nela o Docker ativa um servidor DNS embutido (127.0.0.11) que resolve o nome do serviço para o IP do contêiner. O `app.py` usa `DB_HOST=db` (definido no `docker-compose.yml`) e, na evidência `09-network-inspect.txt`, o `db` aparece com o IP 172.19.0.2. Se os contêineres fossem criados com `docker run` na rede bridge padrão, não haveria esse DNS: o `web` teria de usar o IP do `db`, que muda a cada recriação, ou usar o `--link`, que é obsoleto. Por isso criar uma rede própria resolve o problema.

**Q2. Volume nomeado x bind mount.** O volume nomeado é criado e gerenciado pelo Docker (em `/var/lib/docker/volumes/.../_data`, ver `15-volume-inspect-dados_banco.txt`), independe da estrutura de pastas do host e é portátil. O bind mount liga um caminho específico do host a um caminho do contêiner, e o conteúdo é o arquivo real da máquina. O `init.sql` é bind mount porque é um arquivo do repositório, versionado e editado por quem desenvolve, e deve ser lido em modo somente leitura (`:ro`). Os dados do banco são volume nomeado porque pertencem ao Docker, não ao repositório, precisam sobreviver ao `down` e não devem depender de permissões nem de caminhos do host.

**Q3. Alterar o `init.sql` depois da primeira subida.** Não, a mudança não é aplicada. A imagem do PostgreSQL só executa os arquivos de `/docker-entrypoint-initdb.d/` quando o diretório de dados está vazio, e o volume `dados_banco` já está preenchido (por isso, na `18-depois-down-v.txt`, os itens de exemplo só voltaram depois do `down -v`). Para aplicar sem perder dados, execute o SQL manualmente no banco em execução, por exemplo `docker compose exec db psql -U $DB_USER -d $DB_NAME -c "ALTER TABLE itens ADD COLUMN ..."`. A alternativa é usar uma ferramenta de migração. Recriar o volume com `down -v` só serve se os dados puderem ser apagados.

**Q4. Por que `depends_on` sozinho não basta?** Sem `condition: service_healthy`, o `depends_on` só garante a ordem de início dos contêineres: o `web` sobe assim que o contêiner `db` está "iniciado". Nesse momento o PostgreSQL ainda pode estar inicializando, rodando o `init.sql` ou preparando o diretório de dados, e não aceita conexões. A primeira tentativa do `psycopg` falharia. No meu `docker-compose.yml`, o healthcheck com `pg_isready` marca o `db` como *healthy* só quando ele aceita conexões, e o `depends_on` com `service_healthy` faz o `web` esperar por isso (ver `13-down-up.txt`, linhas "Waiting" e "Healthy").

**Q5. Ordem `COPY requirements.txt` → `RUN pip install` → `COPY app.py`.** O Docker guarda cada instrução como uma camada em cache e só reaproveita a camada se ela e todas as anteriores não mudaram. Como o `requirements.txt` muda raramente, a camada do `pip install` fica em cache e a instalação (a parte mais lenta) não se repete. O `app.py` muda toda hora, então vem por último. Quando só o `app.py` muda, o Docker reaproveita todas as camadas até o `pip install` e refaz apenas o `COPY app.py` e o que vier depois. A captura `01b-build-docker-desktop.png` mostra o build com 11 etapas.

**Q6. Por que não publicar a porta 5432 e relação com a LGPD.** Publicar a 5432 exporia o banco a qualquer máquina que alcance o host, permitindo ataques de força bruta ou uso de credenciais vazadas. No meu `docker-compose.yml`, o `db` não tem `ports`, e a `01-compose-ps.txt` mostra só `5432/tcp`, sem mapeamento. Fotos de documentos pessoais (carteira de estudante, RG) são dados pessoais sob a LGPD, que exige medidas de segurança contra acesso não autorizado (princípio da segurança, art. 6º, VII, e art. 46). Isolar o banco na rede interna é uma dessas medidas. Duas medidas adicionais: (1) autenticação e controle de acesso nas rotas `/fotos/<nome>` e `/itens`, hoje abertas a quem alcança a porta 8080, mais HTTPS na frente do `web`; (2) criptografia em repouso dos volumes, com prazo de retenção definido e exclusão das fotos depois que o objeto for devolvido.

**Q7. `docker compose up -d --scale web=3`.** Falha: o `web-2` não inicia porque a porta 8080 do host já está em uso (`19-scale-web3.txt`: "Bind for 0.0.0.0:8080 failed: port is already allocated"). O `ports: "8080:5000"` prende uma porta fixa do host a um único contêiner. Para rodar três réplicas seria preciso remover essa publicação fixa e colocar na frente um balanceador ou proxy reverso (por exemplo nginx), que receberia a 8080 e distribuiria entre as réplicas pela rede interna. As réplicas poderiam compartilhar o volume `fotos` no mesmo host, já que os nomes dos arquivos são UUIDs e não colidem. Mas isso não é seguro nem escalável em vários nós, porque um volume local pertence a um único host. Em produção, as fotos devem ir para um armazenamento de objetos ou um sistema de arquivos compartilhado.

## 5.1 Do ambiente local para a nuvem

| Peça do ambiente local | Microsoft Azure | AWS | Google Cloud |
| --- | --- | --- | --- |
| Contêiner web | Azure Container Apps | Amazon ECS com Fargate | Cloud Run |
| Contêiner db + volume dados\_banco | Azure Database for PostgreSQL (Flexible Server) | Amazon RDS for PostgreSQL | Cloud SQL for PostgreSQL |
| Volume fotos | Azure Blob Storage | Amazon S3 | Cloud Storage |
| rede\_interna | Virtual Network (VNet) com subnets privadas e NSG | VPC com subnets privadas e security groups | VPC com regras de firewall |
| Arquivo .env (segredos) | Azure Key Vault | AWS Secrets Manager | Secret Manager |
| Imagem construída localmente | Azure Container Registry (ACR) | Amazon ECR | Artifact Registry |

A peça que mais muda é o volume `fotos`. Hoje o `app.py` grava e lê as fotos como arquivos em `/app/uploads` (com `foto.save` e `send_from_directory`), o que depende de um disco local montado no contêiner. Na nuvem, os contêineres são descartáveis e podem rodar em várias réplicas, como mostrou o teste do `--scale web=3`, e um volume local não é compartilhado entre elas. As fotos precisam ir para um armazenamento de objetos (Blob Storage, S3 ou Cloud Storage), acessado por API, e isso exige alterar o código da aplicação. As outras peças mudam de serviço, mas quase sem mexer no código: o banco passa a ser gerenciado e só troca as variáveis `DB_*`, e os segredos saem do `.env` para um cofre.
